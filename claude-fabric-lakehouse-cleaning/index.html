Microsoft Fabric + Claude Code

Use Claude to design data cleaning for a Fabric lakehouse

A step-by-step guide to using Claude as a read-only, in-between layer. It explores your lakehouse data, proposes cleaning rules, and writes a PySpark notebook. You review everything and run the notebook in Fabric yourself. Nothing in OneLake changes until you choose to run the code.

Claude1. ReadQueries the lakehouse through its read-only SQL endpoint
Claude2. ProfileFinds nulls, duplicates, bad formats and outliers
You3. Approve rulesReview the proposed cleaning rules and change any you disagree with
Claude4. Write codeGenerates a PySpark notebook file on your machine
You + Fabric5. RunImport, review, and run it in Fabric, writing to Silver

Example names used below: workspace Analytics, source lakehouse lh_sales_bronze, target lakehouse lh_sales_silver. Replace them with yours.

1Install the tools

Run these in Windows PowerShell. Open a new terminal after each install.

  1. Install Azure CLI if you don't have it, then confirm it works: 
    winget install Microsoft.AzureCLI
az --version
  2. Install Claude Code with Anthropic's native installer: 
    irm https://claude.ai/install.ps1 | iex
claude --version
    If claude isn't recognized, open a new terminal so your PATH refreshes. WinGet works too: winget install Anthropic.ClaudeCode, but it doesn't auto-update.
  3. Install Git for Windows (recommended): winget install Git.Git
  4. Create a project folder for this work, and start Claude Code there once to sign in to your Claude account: 
    mkdir C:\Work\lakehouse-cleaning
cd C:\Work\lakehouse-cleaning
claude
    Follow the sign-in prompts, then type /exit to close.

2Connect Claude Code to Fabric

Microsoft's Skills for Fabric plugin gives Claude Fabric know-how and registers Fabric's remote MCP servers, including the SQL endpoint server. It reuses your Azure CLI sign-in, so no app registration or copied tokens are needed.

  1. Sign in to Azure CLI with the account that has Fabric access. If your account has no Azure subscriptions, add the flag shown: 
    az login --tenant <your-tenant-id> --allow-no-subscriptions
az account show --query tenantId --output tsv
    The second command should print your Fabric tenant ID. If you use more than one account, make sure this is the one with lakehouse access.
  2. Install the plugin from your project folder: 
    claude plugin marketplace add microsoft/skills-for-fabric
claude plugin install fabric-skills@fabric-collection
claude mcp list
    The older fabric-consumption bundle is retired. It now just installs fabric-skills.
  3. Check that the servers connected. Start claude and type /mcp. You should see the plugin's Fabric servers, including the SQL endpoint server, as connected. Note their exact names, which you need in step 3.
  4. Run a connection test inside Claude Code:
    PROMPTUsing the Fabric SQL endpoint, list the tables in the lakehouse lh_sales_bronze in workspace Analytics. Read-only: run only SELECT statements.
    Claude asks permission before each tool call. Approve it, and you should get a list of tables.
Why this path: the lakehouse SQL analytics endpoint is read-only for Delta tables. You can query it and create views, but INSERT, UPDATE and DELETE aren't possible there. That makes it a safe place for Claude to look at your data.

3Keep Claude read-only

Claude acts as your signed-in account, so it can do anything you can do. These three layers keep it to looking and writing local files.

3a. Write house rules in a CLAUDE.md file

Claude Code reads CLAUDE.md in the project folder at the start of every session. Create C:\Work\lakehouse-cleaning\CLAUDE.md:

# Rules for this project
- Microsoft Fabric is READ-ONLY in this project.
- Only run SELECT queries against Fabric. Never run CREATE, ALTER, DROP,
  INSERT, UPDATE, DELETE, MERGE, or anything that changes data or items.
- Never create, run, or modify Fabric notebooks, pipelines, lakehouses, or
  any other Fabric item. Never call Fabric REST APIs that write.
- Prefer aggregate profiling queries. Pull at most 20 sample rows per table.
- Never print or display full columns of personal data.
- All generated code is saved locally in ./output for the user to review.

3b. Block the write-capable server

The plugin also registers a Power BI authoring server, which can change semantic models. You don't need it here, so deny it. Create .claude\settings.json in the project folder:

{
  "permissions": {
    "deny": [
      "mcp__plugin_fabric-skills_powerbi-modeling-mcp__*"
    ]
  }
}

Plugin servers use the form mcp__plugin_<plugin>_<server>__*. If the name in /mcp is different, use that name. Run claude doctor to confirm the rule loaded without errors.

3c. Approve tool calls yourself

  • Stay in the default permission mode. Don't use auto-approve or bypass modes for this project.
  • Read every SQL statement before approving it. Approve only SELECT queries.
  • Don't choose "always allow" for the SQL tool. Claude Code can't filter by statement type, so your review is the control.
  • Be careful with shell commands too. Approve az or curl calls only if they read data.
Result: Claude can look at the lakehouse, but every action needs your approval, it has no authoring server, and the lakehouse endpoint itself can't modify tables.

4Profile the data

Start with summary statistics. They tell Claude most of what it needs without sending raw rows to Anthropic.

PROMPT 1: INVENTORYList every table in lh_sales_bronze (workspace Analytics) with its row count, column names, and data types. Read-only.
PROMPT 2: PROFILEFor each table, profile every column using aggregate SELECT queries only: - null and empty-string percentage - distinct count, and the top 10 values with their counts for low-cardinality columns - min, max, and average for numeric and date columns - values that don't match the expected type (text in numeric columns, unparseable dates) - leading or trailing spaces and inconsistent casing - duplicate rows on the likely business key Pull at most 20 sample rows per table, and only if needed. Save the results to ./output/profile.md with one section per table, and a summary of the biggest issues at the top.

For large tables, ask Claude to add TOP or a sampling filter to its queries to keep them fast.

5Agree the cleaning rules

This is the most important step. Claude proposes the rules, and you decide which ones apply.

PROMPT 3: PROPOSE RULESBased on ./output/profile.md, propose data cleaning rules. Save them to ./output/cleaning-rules.md as a table with these columns: table | column | issue found | proposed rule | rows affected (estimate) | risk if wrong | needs business input (yes/no) Group the rules into: type fixes, standardization, null handling, deduplication, invalid or out-of-range values, and derived columns. Don't write code yet.

Then review the file and reply in chat, for example:

PROMPT 4: REFINERule 4: don't drop rows with a null region, set the region to 'Unknown' instead. Rule 7: dedupe on order_id and keep the latest by modified_date. Remove rule 9. Mark everything else as approved and update the file.
Decide these yourself, not Claude: what counts as a duplicate, whether to drop or quarantine bad rows, default values for nulls, and anything with business meaning, such as currency, fiscal dates, or status codes.

6Generate the notebook

PROMPT 5: WRITE THE NOTEBOOKTurn the APPROVED rules in ./output/cleaning-rules.md into a Microsoft Fabric PySpark notebook saved as ./output/clean_bronze_to_silver.ipynb. Do not run it and do not upload it to Fabric. Structure: 1. A parameters cell with source and target ABFS paths, the table list, and a dry_run flag that defaults to True. 2. Read each source table as Delta. 3. One clearly named function per rule, each with a comment that cites the rule number. 4. Bad rows go to a separate quarantine table instead of being silently dropped. 5. Data quality checks with row counts before and after each rule, a null check on key columns, and a uniqueness check on the business key. 6. When dry_run is True, only display results. When it's False, write cleaned tables to the target path with mode "overwrite" and never write to the source path. 7. A final summary cell showing rows in, rows out, and rows quarantined per table. Use only PySpark built into the Fabric runtime. No extra libraries.

Ask follow-ups until you're happy with it, for example "explain cell 4", "make rule 7 deterministic", or "add a check that no new nulls appear in customer_id".

You can find the ABFS paths in Fabric. Open the lakehouse, select Tables (or a table), open the ... menu, and choose Properties to copy the ABFS path. They look like abfss://<workspace>@onelake.dfs.fabric.microsoft.com/<lakehouse>.Lakehouse/Tables/...

7Run it in Fabric

  1. Create the Silver lakehouse if it doesn't exist. In the workspace, select New item > Lakehouse and name it lh_sales_silver.
  2. Import the notebook. In the workspace toolbar, choose Import > Notebook > From this computer and pick clean_bronze_to_silver.ipynb. Fabric accepts standard .ipynb files.
  3. Attach the lakehouses. Open the notebook, add both lakehouses in the explorer pane, and pin lh_sales_silver as the default.
  4. Fill in the parameters cell with the real ABFS paths. Leave dry_run = True.
  5. Run the cells one at a time. Read each cell before running it. Check the before and after counts and the quarantine counts.
  6. Do the real run. When the dry run looks right, set dry_run = False and run the notebook again. Cleaned tables appear in lh_sales_silver, and Bronze is untouched.
Note: interactive notebook runs use your identity and your workspace's Fabric capacity. If something goes wrong, Delta time travel lets you go back to an earlier version of a Silver table.

8Validate and iterate

PROMPT 6: VALIDATEProfile the cleaned tables in lh_sales_silver the same way as before, read-only. Compare them with ./output/profile.md and confirm each approved rule had the expected effect. Flag anything unexpected, and save the result to ./output/validation.md.
  • If something is off, update the rules file and regenerate the notebook. Then re-import it, or paste the changed cells into Fabric.
  • Keep the output folder, or put it in Git. The profile, rules, and validation files are your documentation.
  • Once the notebook is stable, you can schedule it in Fabric or add it to a pipeline. Claude doesn't need to be involved after that.

Alternatives without the plugin

A. Read a sample locally with Python

Claude Code writes and runs a local script that reads a Delta table straight from OneLake and profiles it on your machine. No MCP is involved.

pip install deltalake polars azure-identity
# profile_sample.py (Claude can write this for you)
from azure.identity import AzureCliCredential
from deltalake import DeltaTable
import polars as pl

token = AzureCliCredential().get_token(
    "https://storage.azure.com/.default").token
path = ("abfss://Analytics@onelake.dfs.fabric.microsoft.com/"
        "lh_sales_bronze.Lakehouse/Tables/orders")
dt = DeltaTable(path, storage_options={
    "bearer_token": token, "use_fabric_endpoint": "true"})
df = pl.from_arrow(dt.to_pyarrow_dataset().head(50000))
print(df.describe())

This needs the tenant setting Users can access data stored in OneLake with apps external to Fabric. The data lands on your laptop, so treat it accordingly. For schema-enabled lakehouses, include the schema, such as Tables/dbo/orders.

B. Claude chat only, no setup

  1. In Fabric, run a profiling query or notebook yourself and export the results, or a small sample, to CSV.
  2. Upload the CSV to a Claude chat and use prompts 3 to 5 above.
  3. Copy the generated notebook into Fabric and run it as in step 7.

This is the most manual option, but it's the easiest to get approved. Claude only sees what you choose to upload.

Troubleshooting

ProblemWhat to check
claude isn't recognizedOpen a new terminal. If it still fails, follow Anthropic's PATH fix in the Claude Code install troubleshooting guide.
Fabric servers show as failed in /mcpRun az account show in the same terminal. Sign in with az login --tenant <id> --allow-no-subscriptions if needed, then restart Claude Code. A successful install doesn't mean every server connected.
Errors about OAuth or dynamic client registrationUsually means the Azure CLI token step failed and the client fell back to OAuth. Fix the az login session first. Also check for an older manual registration with the same server name that overrides the plugin's.
Wrong tenant or no tables foundConfirm az account show prints the tenant that holds the workspace, and that your account can open the lakehouse SQL endpoint in the Fabric portal.
New Bronze data isn't visibleThe SQL endpoint usually syncs within a minute. You can refresh its metadata from the SQL endpoint in Fabric.
The notebook fails on a pathRe-copy the ABFS paths from table Properties. Check whether the lakehouse uses schemas, which adds dbo/ to the path.

Data handling and security

What leaves Fabric

  • Everything Claude reads, including query results, samples, and schema, is sent to Anthropic as conversation context.
  • Microsoft's MCP guidance says these clients may process data outside the Fabric compliance boundary, under the client's terms.
  • Sensitivity labels and DLP don't follow data into Claude.
  • Keep it to aggregates. Don't sample columns that contain personal data.

What protects your data

  • The lakehouse SQL endpoint can't modify Delta tables.
  • Your Fabric permissions, plus row-level and object-level security, still apply to every query.
  • CLAUDE.md rules, the deny rule, and your approval of each tool call.
  • You run the notebook yourself, after reviewing it, writing to Silver only.

Final checklist

  • Approval to share this data with Claude
  • Azure CLI signed in to the right tenant, and Fabric servers connected in /mcp
  • CLAUDE.md and the deny rule in place, with no auto-approve
  • Profile and rules reviewed, and business rules decided by you
  • Notebook reviewed, dry run checked, writing to Silver only
  • Silver validated against the original profile
