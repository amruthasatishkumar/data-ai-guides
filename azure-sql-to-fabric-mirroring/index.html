Mirror an Azure SQL Database into Microsoft Fabric

A practical, interactive how-to for Fabric mirroring: a managed, no-ETL way to keep a read-only, analytics-ready copy of your Azure SQL Database tables in OneLake. Learn how it works, what to prepare, how to choose networking and authentication, how to set it up and check it, and where the limits and costs are.

1What database mirroring is

Mirroring continuously replicates data from an operational database into OneLake, the single data lake behind Microsoft Fabric. You don't build or schedule pipelines. Fabric manages the replication.

What it does

  • Takes an initial snapshot of the tables you choose, then keeps them in sync in near real time.
  • Stores the copy as Delta Lake tables (Parquet files) in OneLake.
  • Gives you a read-only SQL analytics endpoint over those tables.
  • You can mirror the whole database or pick individual tables.

What it isn't

  • Not a writable copy. You can't insert, update or delete mirrored data through the SQL analytics endpoint.
  • Not a backup or failover target for your Azure SQL Database.
  • Not a transformation tool. Shape data afterwards with views, notebooks or other Fabric items.
  • Not the same as SQL database in Fabric, which is a database created inside Fabric that mirrors itself automatically.

Three kinds of mirroring

  • Database mirroring copies tables into OneLake. Azure SQL Database uses this kind.
  • Metadata mirroring syncs catalog metadata and uses shortcuts, so data stays in the source.
  • Open mirroring lets an application write change data into a mirrored database through public APIs.
Good fit: you want reporting, analytics, data science or AI over operational data without running heavy queries on the production database and without maintaining ETL jobs. Mirroring is described by Microsoft as low cost and low latency, with near real-time replication.

2How it works

Select a stage to see what happens.

When you start mirroring, Fabric copies the current contents of every selected table. How long this takes depends on the size of the data.

  • The snapshot and later change data land first in a landing zone in OneLake, inside your own tenant. Data isn't staged outside your environment.
  • During the snapshot, expect extra CPU and IOPS on the source database while pages are read.
  • In the portal, table status moves to Running, and a date appears in Last completed when a table's initial copy is done.
  • Stopping and restarting replication, or certain schema changes, cause a new snapshot (a reseed) of the affected tables.

After the snapshot, the source publishes committed inserts, updates and deletes from its transaction log. Inside Fabric, a replicator engine scans for newly published files and merges them into the target Delta tables.

  • Microsoft describes the latency as near real time. Its overview says changes can be published as fast as every 15 seconds, and backoff logic reduces overhead when activity is low.
  • Actual latency depends on the source and destination regions, the volume and frequency of changes, and network bandwidth (plus gateway resources if you use an on-premises data gateway).
  • Active transactions hold back log truncation until they commit and mirroring catches up. Watch the source transaction log during long-running transactions.
  • There's a maximum of 1 TB of change data captured per mirrored database per day. Above that, replication is throttled until the next window.

Mirrored data is stored in OneLake as V-Ordered Delta Lake tables, an open format that Spark, Power BI and many other tools can read.

  • The source schema hierarchy (for example dbo, sales) is preserved for newly created mirrored databases.
  • Mirroring automatically runs vacuum to remove old Delta files. For mirrored databases created in the portal after mid-June 2025, the default retention is one day. You can change it under Settings > Delta table management.
  • Delta stores six fractional-second digits, so datetime2(7) values lose the seventh digit. See Limitations.

Each mirrored database gets an autogenerated, read-only SQL analytics endpoint. It's the same experience as the lakehouse SQL analytics endpoint.

  • Query tables with T-SQL in the Fabric SQL query editor, SQL Server Management Studio, or the MSSQL extension for Visual Studio Code.
  • Create views, inline table-valued functions and stored procedures to hold business logic.
  • Manage permissions on objects, and query other warehouses and lakehouses in the same workspace.
  • New data can take a moment to appear here after it lands in OneLake because of metadata sync. You can force a refresh from the endpoint page.
Changed in 2025: since September 5, 2025, Fabric no longer creates a default Power BI semantic model when you create a mirrored database. By November 30, 2025, existing default semantic models were disconnected from their items and became independent semantic models.

If you need a semantic model, create one yourself from the mirrored database's SQL analytics endpoint. New semantic models created on a warehouse or SQL analytics endpoint use Direct Lake storage mode, which reads the Delta files directly. Because the mirrored tables are V-Ordered Delta tables, Power BI reports on mirrored data can use Direct Lake.

4Choose networking

Mirroring needs two connections: Fabric connects in to your logical server to set up and monitor mirroring, and the database connects out to OneLake, using its managed identity, to publish data.

5Choose authentication

Two identities are involved, and they do different jobs.

Server managed identity: writes to OneLake

The logical server's SAMI or UAMI Preview publishes data to OneLake. It must be enabled and must be the server's primary identity. When you create the mirror in the Fabric portal, this identity is automatically granted Read and write on the mirrored database item. Don't remove that permission.

Connection principal: Fabric reads the source

Fabric connects to the database with a principal you create, with the four permissions listed below. Pick the type in the chooser. Follow least privilege and use a dedicated principal rather than an admin account.

Good for: quick tests, or when Microsoft Entra authentication isn't set up on the server. Store the password safely and rotate it per your policy. In Fabric, choose Basic and enter the user name and password.

-- 1. In the master database
CREATE LOGIN [fabric_login] WITH PASSWORD = '<strong password>';

-- 2. In the user database you will mirror (SalesDB)
CREATE USER [fabric_user] FOR LOGIN [fabric_login];
GRANT SELECT, ALTER ANY EXTERNAL MIRROR,
      VIEW DATABASE PERFORMANCE STATE, VIEW DATABASE SECURITY STATE
   TO [fabric_user];

Microsoft's security guidance also allows a contained database user with a strong password instead of a login.

Good for: organizations that standardize on Microsoft Entra ID. Sign in as the server's Microsoft Entra admin to run this. In Fabric, choose Organizational account.

Preview: Microsoft Entra server principals (logins) are in preview for Azure SQL Database. Users created from Entra logins can see delays when roles and permissions are granted. See Troubleshooting for the documented fix.
-- 1. In the master database
CREATE LOGIN [user@contoso.com] FROM EXTERNAL PROVIDER;

-- 2. In SalesDB
CREATE USER [user@contoso.com] FOR LOGIN [user@contoso.com];
GRANT SELECT, ALTER ANY EXTERNAL MIRROR,
      VIEW DATABASE PERFORMANCE STATE, VIEW DATABASE SECURITY STATE
   TO [user@contoso.com];

Good for: a non-person identity that isn't tied to an employee account. In Fabric, choose Service principal and enter the tenant ID, client ID and client secret.

-- 1. In the master database (as the Microsoft Entra admin)
CREATE LOGIN [<service principal name>] FROM EXTERNAL PROVIDER;

-- 2. In SalesDB
CREATE USER [<service principal name>] FOR LOGIN [<service principal name>];
GRANT SELECT, ALTER ANY EXTERNAL MIRROR,
      VIEW DATABASE PERFORMANCE STATE, VIEW DATABASE SECURITY STATE
   TO [<service principal name>];

Good for: avoiding stored secrets by using the Fabric workspace identity. In Fabric, choose Workspace identity.

-- 1. In the master database (as the Microsoft Entra admin)
CREATE LOGIN [<workspace identity name>] FROM EXTERNAL PROVIDER;

-- 2. In SalesDB
CREATE USER [<workspace identity name>] FOR LOGIN [<workspace identity name>];
GRANT SELECT, ALTER ANY EXTERNAL MIRROR,
      VIEW DATABASE PERFORMANCE STATE, VIEW DATABASE SECURITY STATE
   TO [<workspace identity name>];

The setup tutorial lists workspace identity as an authentication kind. The Azure SQL mirroring FAQ currently lists only SQL authentication, Microsoft Entra ID and service principal, so confirm availability in your tenant.

ALTER ANY EXTERNAL MIRROR is also included in higher-level permissions such as CONTROL or the db_owner role, but granting only the four permissions above follows least privilege.

6Step-by-step setup

Follow these in order. Steps 1 to 3 happen in Azure, steps 4 to 8 in the Fabric portal.

  1. Enable the server's managed identity
    1. In the Azure portal, open your logical SQL server (not the database).
    2. Under Security, select Identity.
    3. Under System assigned managed identity, set Status to On and save.
    4. Confirm it's the primary identity with the query below.
    1. Create a user-assigned managed identity if you don't have one.
    2. On the logical server, under Security > Identity, add the UAMI as the primary identity.
    3. If the database is already mirrored with SAMI, first grant the UAMI Read and write on the mirrored database item (... > Manage permissions > Add user, matching the AppID to client_id), then make it primary. Keep the old identity's permissions for at least 15 minutes.
    -- Run on the logical server. is_primary = 1 shows the identity mirroring will use.
SELECT * FROM sys.dm_server_managed_identities;
  2. Open a network path

    Use the networking helper. If you need a gateway, create a virtual network data gateway or install an on-premises data gateway before you create the connection. If the target workspace restricts inbound OneLake access, ask a workspace admin to add the server's Azure resource ID as a Resource Instance Rule.

  3. Create the database principal for Fabric

    Connect to the server with SSMS or the MSSQL extension for VS Code, then run the script for your authentication choice: create the login in master, then the user and the four grants in SalesDB.

  4. Create the mirrored database item

    In the Fabric portal, open a workspace where you're Admin or Member. Select Create, scroll to Data Warehouse, and choose Mirrored Azure SQL Database. Give it a name, then select Create.

  5. Connect to the source

    Under New sources, choose Azure SQL Database (or reuse an existing connection from the OneLake hub) and fill in:

    FieldValue
    Server<your-server>.database.windows.net, from the database's Overview page. For geo-failover, use the failover group's read-write listener.
    DatabaseSalesDB
    Connection / nameCreate a new connection. An automatic name is suggested.
    Data gatewayNone for public access, or your virtual network or on-premises data gateway.
    Authentication kindBasic, Organizational account, Service principal, or Workspace identity, matching step 3.

    Select Connect.

  6. Choose what to mirror
    • Mirror all data (default): includes tables created later. If there are more than 1,000 tables, only the first 1,000 sorted by schema name then table name are mirrored.
    • Select tables: clear Mirror all data and pick tables. You can't select more than 1,000.
  7. Start mirroring and watch it come up

    Select Mirror database. Wait 2 to 5 minutes, then select Monitor replication. Status should change to Running. When a table's initial copy finishes, a date appears in the last refresh or Last completed column. If tables don't show yet, wait a few seconds and refresh the panel.

  8. Prove it end to end

    Make one small, harmless change in a test source database, then read it from Fabric. The table and column names here are examples.

    -- A. In Azure SQL Database (the source), on a test row
UPDATE dbo.Orders
SET    Status = N'Mirroring check', ModifiedUtc = SYSUTCDATETIME()
WHERE  OrderId = 1001;

SELECT OrderId, Status, ModifiedUtc FROM dbo.Orders WHERE OrderId = 1001;
    -- B. In Fabric, on the mirrored database's SQL analytics endpoint (read-only)
SELECT OrderId, Status, ModifiedUtc,
       (SELECT COUNT(*) FROM dbo.Orders) AS OrderCount
FROM   dbo.Orders
WHERE  OrderId = 1001;

    Compare the value and timestamp. If they don't match yet, wait and rerun the read query, rather than repeating the update. Replication is near real time, not instant.

Don't skip this: row-level security, column (object-level) permissions, dynamic data masking and sensitivity labels in the source are not carried over. Reconfigure the security you need in Fabric before you share the mirrored data. See Security.

7What you get after mirroring

Mirrored database item

Manages replication and its settings: tables, retention, connection, and replication status. Mirrored databases are an item in Fabric Data Warehousing, separate from the Warehouse item.

SQL analytics endpoint

Read-only T-SQL over the Delta tables. Add views, inline TVFs, stored procedures and object permissions. Works with the Fabric query editor, SSMS and VS Code.

Delta tables in OneLake

Open-format tables that other Fabric engines can use. For example, create a lakehouse shortcut to the mirrored tables and query them from Spark notebooks.

Power BI with Direct Lake

Create a semantic model on the SQL analytics endpoint and report in Direct Lake mode, without importing the data. No default model is created for you.

Cross-database queries

Join mirrored tables with warehouses and lakehouse SQL analytics endpoints in one T-SQL query, using three-part names.

Item-level sharing

Share the mirrored database without giving workspace access. Options include "Read all SQL analytics endpoint data" and "Read all OneLake data".

Example: rebuild a computed column on the Fabric side

Computed columns aren't mirrored. Recreate the logic in a view on the SQL analytics endpoint (example names):

-- On the SQL analytics endpoint of the mirrored database
CREATE VIEW dbo.vw_OrderLines AS
SELECT OrderId, LineNumber, Quantity, UnitPrice,
       Quantity * UnitPrice AS LineTotal   -- was a computed column in the source
FROM   dbo.OrderLines;

8Monitoring

Open the mirrored database and select Monitor replication.

StatusMeaning
RunningSnapshot and change data are flowing into OneLake.
Running with warningReplication continues, with transient (database) or nonfatal (table) errors.
Stopping / StoppedReplication has stopped.
FailedA fatal error that replication can't recover from.
PausedDatabase level only. Happens after the Fabric capacity is paused and resumed. Select Resume replication.

Per table you also see Rows replicated (cumulative inserts, updates and deletes) and Last completed. An empty Last completed means the table isn't mirrored yet.

Turn on workspace monitoring in workspace settings. Mirrored database execution logs then flow into the MirroredDatabaseTableExecution table in the monitoring KQL database. Query them with KQL, build Power BI or Real-Time Dashboards, and set alerts. To check latency, query the ReplicatorBatchLatency value in these operation logs.

The Microsoft Fabric mirroring public REST API (and SDK) can return mirroring status for a mirrored database and for specific tables. It's useful for automated health checks. If you create mirrored databases through the API or CI/CD, you must also grant the server's managed identity Read and write on the item yourself.

Run these on the source Azure SQL Database:

-- Are changes flowing?
SELECT * FROM sys.dm_change_feed_log_scan_sessions;

-- Any errors reported?
SELECT * FROM sys.dm_change_feed_errors;

-- Per-table configuration. A state other than 4 suggests a problem.
EXEC sp_help_change_feed;

-- Is mirroring holding up log truncation? Look for REPLICATION.
SELECT [name], log_reuse_wait_desc
FROM   sys.databases
WHERE  is_data_lake_replication_enabled = 1;

9Limitations

Microsoft notes that this list is subject to change. Check the limitations page before you commit to a design.

Table checker: will this table mirror?

Tick everything that applies to one source table.

Database level

  • Only a writable primary database can be mirrored.
  • Not supported if CDC, Azure Synapse Link for SQL, or delayed transaction durability is enabled.
  • Each database can be mirrored only once (not into a second Fabric workspace).
  • Maximum 1,000 mirrored tables per database.
  • .dacpac deployments need the publish property /p:DoNotAlterReplicatedObjects=False to change mirrored tables.
  • No cross-tenant mirroring.

Schema changes and operations

  • Switch partition and alter primary key aren't allowed on mirrored source tables.
  • DDL changes, such as add, drop, alter or rename column, or truncate or rename table, trigger a full reseed of that table.
  • You can't alter a column to json or vector while the table is mirrored.
  • Stopping mirroring disables it completely. Starting again reseeds every table.
  • You can't change the source database of a mirror. Create a new one.
  • Ownership of a mirrored database can't be transferred. If the owner leaves, recreate it.

Data and types

  • Delta supports six fractional-second digits: datetime2(7) loses its seventh digit, and datetimeoffset(7) also loses the time zone.
  • LOB columns over 1 MB are truncated to 1 MB in OneLake.
  • On the SQL analytics endpoint, varchar(max) for mirrored Azure SQL Database is limited to 1 MB. Tables created before November 18, 2025 support only varchar(8000) until recreated.
  • Tables without a primary key can be mirrored since April 2025. Older mirrors may need replication restarted to pick them up.

Security and endpoint

  • Row-level security, object-level permissions, dynamic data masking and Purview sensitivity labels aren't propagated to OneLake.
  • The SQL analytics endpoint is read-only and shares the lakehouse SQL analytics endpoint's limitations.
  • Only one copy per source: share it rather than mirroring again.
  • Available in all Microsoft Fabric regions.

11Security considerations

Where the data goes

  • According to the FAQ, data doesn't leave your Fabric tenant and isn't staged outside your environment. The landing zone is in your OneLake.
  • Deleting the mirror doesn't affect the source database.
  • Removing a table from mirroring deletes its data from OneLake.
  • Mirroring into a workspace with restricted inbound OneLake access works when the server is added as a Resource Instance Rule.

What you must set up again in Fabric

  • Source row-level security, column permissions and dynamic data masking don't carry over.
  • Recreate them with row-level security, column-level security and dynamic data masking in Fabric data warehousing, or with OneLake security Preview.
  • "Read all OneLake data" gives direct access to the mirrored files, for example with Spark. Grant it only to people who should see all of the data.

Least privilege

  • Use a dedicated principal with only the four required permissions.
  • Don't remove the server identity's Read and write permission on the mirrored item, or replication stops.
  • Share the mirrored database item instead of granting workspace roles, where possible.

Network

  • Microsoft notes that "Allow Azure services" is often more permissive than customers want. For sensitive data, consider private connectivity (a gateway plus a private endpoint) instead.
  • With a network security perimeter Preview, start in transition mode, add the inbound and outbound rules, and switch to enforced mode only after replication is current and logs are clean.
  • Use the item-level OneLake FQDN for the outbound rule, never a wildcard.

13FAQ

Is mirroring Azure SQL Database generally available?
It's listed on Microsoft Learn without a preview label, unlike sources such as Azure Database for MySQL that are marked preview. Some related features are in preview: user-assigned managed identity, network security perimeter support, and Microsoft Entra server logins for Azure SQL Database.
How fast do inserts, updates and deletes show up?
Microsoft describes it as near real time. Latency depends on regions, change volume and frequency, and network bandwidth. Plan for a short delay, and measure it with workspace monitoring (ReplicatorBatchLatency) if it matters.
How long does the initial replication take?
It depends on how much data you're mirroring. Watch the Last completed column in Monitor replication.
Can I mirror views?
No. Only regular tables are replicated from Azure SQL Database. Mirroring views is an extended capability currently in preview for Snowflake only. You can recreate view logic as views on the SQL analytics endpoint.
Can I write to the mirrored tables?
No. The mirrored copy and its SQL analytics endpoint are read-only. You can create views, functions and stored procedures on the endpoint, but not change the data.
Can I mirror the same database twice?
No. Each Azure SQL Database can be mirrored only once. Share the mirrored database with other people or workspaces instead.
What happens if I stop mirroring, or restart it?
When you stop, replication stops but the copied tables stay in OneLake. When you start again, every table is reseeded from scratch.
What if I pause my Fabric capacity?
No data is replicated while the capacity is paused, and you pay normal OneLake storage rates for mirrored data during the pause. After you resume, select Resume replication. After a long pause, mirroring may reseed the whole database.
What does mirroring cost?
Replication compute is free, and mirrored storage is free up to 1 TB per capacity unit. Querying the data uses your capacity at regular rates. Cross-region egress is charged. See Costs.
Which licenses do I need?
A Power BI Premium capacity, a Fabric capacity, or a trial capacity.
Does mirroring slow down my production database?
It adds load, mostly during the initial snapshot (CPU and IOPS), and updates and deletes can increase log generation. Long-running transactions can hold log truncation. Monitor the source and its transaction log, and start on a test copy.
Can I use Power BI Direct Lake on mirrored data?
Yes. Mirrored tables are V-Ordered Delta tables. Create a semantic model on the SQL analytics endpoint, because a default semantic model is no longer created automatically.
What happens during a geo-failover?
Replication is disabled automatically, though the portal may look unchanged. Stop and start replication to resync. Connecting through the failover group's read-write listener means you don't have to recreate the mirror.
Does deleting the mirror affect my Azure SQL Database?
No. Deleting the mirror removes the replicated data in Fabric, not your source data.
My database is in another Microsoft Entra tenant. Can I still mirror it?
No. Mirroring across Microsoft Entra tenants, where the database and the Fabric workspace are in different tenants, isn't supported.
