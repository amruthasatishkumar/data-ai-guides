Migration guide

Moving Snowflake from AWS to Azure using Snowgrid

How the migration works using Snowflake's built-in cross-cloud capabilities (Snowgrid), what you set up on the Azure side, and what it costs, including data transfer (egress) fees.

1. What is Snowgrid

Three points to frame the rest of this guide.

What Snowgrid is

The cross-cloud layer

Snowflake describes Snowgrid as its cross-cloud technology layer, connecting accounts across regions and across AWS, Azure and Google Cloud. In practice, that means data and account setup can be replicated between accounts, and clients can be redirected from one account to another.

What stays the same

Snowflake stays Snowflake

Same platform, same SQL, same roles and warehouses. Only the cloud the account runs on changes. There is no separate product to install, just built-in features used between accounts in your Snowflake organization.

Why this approach

Migration is a supported use

Snowflake's documentation lists migration as a use of replication and failover: move your account to a different region or cloud platform without disrupting your business.

In plain terms: you create a Snowflake account on Azure, keep it in sync with your AWS account, test it side by side, then switch your users to the Azure copy. If your clients connect through a Client Redirect connection URL, they keep the same address through the cutover.
Check your edition first. Database and share replication work on every edition. Failover groups, replication of other account objects (users, roles, warehouses, integrations and more) and Client Redirect require Business Critical Edition or higher. For a one-time account migration, Snowflake's documentation says Snowflake Support can temporarily lift the restriction on account object replication and failover without changing your edition. Confirm the scope of that exception with Snowflake Support before you plan around it.

2. Your migration at a glance

Two accounts matter: the AWS account you have today (source) and a new Azure account (target), both in the same Snowflake organization.

Eight concepts, all in one view. Items 1 to 5 are the migration itself. Items 6 to 8 apply in some situations or are checks rather than things to build.

Role grants replicate when roles are in scope.Include the databases that hold your policies and tags. Tag assignments are read-only on the target. 8Encryption and networkReplicated data is protected in transit and at rest and encrypted in the target account under that account's own key hierarchy.Target accounts do not have Tri-Secret Secure or private connectivity enabled by default. If you use them, set them up on the Azure account yourself.

Order matters at cutover. For the most consistent failover, Snowflake's documentation recommends selecting all applicable failover groups and connections and promoting them at the same time (a "bulk failover" in Snowsight), so the data and the URL move together. For a planned cutover, also pause ingestion on AWS and let a final refresh complete first.

6. What moves, what does not

Based on Snowflake's replication documentation. Object-level rules change over time, so confirm each one against your own inventory and the current replicated objects list before cutover.

Can replicate
  • Databases and most objects inside them, with data (all editions)
  • Outbound shares (all editions)
  • Users and their properties, roles and role hierarchies, with grants
  • Warehouses (replicated in the suspended state), resource monitors
  • Network policies and account-level parameters
  • Security, API, notification, storage and external access integrations
  • Stages and pipes (with replication or failover groups)
  • Listings with auto-fulfillment, external volumes for Snowflake-managed Iceberg tables
  • Cortex Search Services, Datasets, workspaces

Databases and shares replicate on every edition. Failover groups and most other account objects need Business Critical or higher. See the edition matrix in Snowflake's documentation for the exceptions.

Does not replicate, or needs care
  • Inbound shares from other providers: not supported
  • External tables, hybrid tables, event tables, temporary tables: not replicated
  • Files on external stages: not copied. Replicated external stages still point to the same S3 location, so plan to move the files to ADLS Gen2 and repoint the stages. Files on user and table stages are not replicated either.
  • Time Travel history and query history: not replicated. Each account keeps its own.
  • Warehouse running state: not carried over
  • Resource monitor email settings for account administrators
  • Privileges on the groups themselves (REPLICATE, FAILOVER): grant on both sides
  • Cloud-side setup outside Snowflake: AWS PrivateLink to Azure Private Link, S3 IAM trust to Azure storage access, plus any SSO and provisioning changes in Microsoft Entra ID

Get your own numbers

Run the first query on your AWS account to size the data. The database storage figure includes Time Travel bytes, which are not replicated, so treat it as an upper bound. Once replication starts, run the second query on the Azure account to see actual transfer and credits (the view can lag by up to three hours).

-- Size of each database over the last 30 days (TB), run on the AWS account
SELECT database_name,
       ROUND(AVG(average_database_bytes) / POWER(1024, 4), 2) AS avg_tb
FROM snowflake.account_usage.database_storage_usage_history
WHERE usage_date >= DATEADD(day, -30, CURRENT_DATE())
GROUP BY database_name
ORDER BY avg_tb DESC;

-- Actual replication transfer and credits, run on the Azure account
SELECT replication_group_name,
       ROUND(SUM(bytes_transferred) / POWER(1024, 4), 3) AS tb_transferred,
       SUM(credits_used) AS credits
FROM snowflake.account_usage.replication_group_usage_history
WHERE start_time >= DATEADD(day, -30, CURRENT_TIMESTAMP())
GROUP BY replication_group_name;
Ways to keep the cost down: replicate only the databases you need, drop tables you no longer need before the first copy, refresh high-churn databases less often, keep the refresh cadence as low as your validation needs, keep the parallel-run window short, and stop refreshing to stop the charges. After the first copy, only changes are sent.

8. Glossary

Organization
The umbrella over all of your Snowflake accounts. Required for cross-account replication.
Account
One Snowflake deployment in one cloud region.
Source and target
The account that holds the primary group (source) and the account that holds the replica (target).
Failover group
A bundle of objects copied from source to target on a schedule, which can also be promoted so the target becomes the writable primary.
Refresh
One synchronization of a secondary group with its primary.
Promote (failover)
Make the secondary the new primary. Objects become writable there and read-only on the old primary.
Failback
Promote the original account to primary again.
Connection and Client Redirect
A named URL that resolves to whichever account holds the primary connection.
Egress
Data transferred out of a cloud or region. Billed per TB.
Listing and auto-fulfillment
An offer of a data product to consumers, which Snowflake can replicate to consumer regions automatically.
Tri-Secret Secure
A Business Critical option that combines a Snowflake-maintained key with a customer-managed key created on the cloud that hosts the account. It is not enabled by default on a target account, so on Azure you set it up with a key you create on Azure.
