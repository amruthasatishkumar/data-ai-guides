Capturing and analyzing Fabric data agent conversations

Fabric data agents don't expose a ready-made, queryable log of what people asked and what the agent answered. This explainer walks through four documented ways to capture those prompts and responses and turn them into something you can analyze, with the caveats that matter for each.

Independent explainer, not official Microsoft guidance. Content checked against Microsoft Learn on November 6, 2026. Several pieces are in preview, so validate behavior in your own tenant.

The challenge

A Fabric data agent lets people ask questions in plain language about data in OneLake. It can draw on lakehouses, warehouses, Power BI semantic models, KQL databases, mirrored databases, ontologies, and Microsoft Graph, and it generates read-only SQL, DAX, or KQL queries to answer. Microsoft documents the data agent as a generally available feature.

The gap is not the agent itself. It's keeping and querying the conversations:

  • In the Fabric chat experience, Clear chat erases the chat history and starts a new session. The docs state that once deleted, the history can't be retrieved.
  • The data agent limitations state that conversation history "might not always persist", and can be reset or lost after backend infrastructure changes, service updates, or model upgrades.
  • When this was checked, the Fabric data agent docs did not describe a built-in, queryable table or report of the prompts and responses of a published data agent. They do mention diagnostics, and Microsoft Purview audit and eDiscovery (in preview).
  • So "save the conversations and analyze them" needs a consumption surface that records the exchange, plus a path into an analytics store.
Key idea: you get a durable record by choosing where the data agent is consumed. Each surface records conversations differently: (A) Copilot Studio writes transcripts to Dataverse; (B) Microsoft 365 Copilot interactions are covered by Microsoft Purview audit, retention, and eDiscovery; (C) your own MCP client can log every request and answer itself; (D) a Microsoft Foundry agent can send traces to Application Insights.

Four approaches

Best for an analytics dataset

A · Copilot Studio + Dataverse + Fabric

Add the published Fabric data agent to a Copilot Studio agent and publish that agent to a channel such as Microsoft Teams. Copilot Studio saves conversation transcripts to the ConversationTranscript table in Dataverse. Link Dataverse to Fabric and analyze in a lakehouse and Power BI.

Best when: you want an ongoing, reusable dataset for usage analytics, unanswered questions, and quality tracking.

Compliance and governance

B · Microsoft 365 Copilot + Microsoft Purview

Publish the data agent to the Agent Store so people use it in Microsoft 365 Copilot. Prompts and responses are stored in a hidden mailbox folder and can be covered by Purview retention, audit, eDiscovery, and Data Security Posture Management (DSPM) for AI.

Best when: the mandate is retention, investigation, or oversight rather than a purpose-built analytics dataset.

Custom apps and pipelines

C · Your own MCP client + your own log

Call the published data agent through its Model Context Protocol (MCP) endpoint from your own app or orchestrator. Your code sends each question and receives each answer, so it can write both to your own store or OneLake.

Best when: the agent is embedded in a custom experience and you want full control over what's captured.

Changed November 6, 2026

D · Microsoft Foundry agent + tracing

Call the data agent from a Foundry agent through the Fabric IQ tool (preview). The older Fabric data agent tool in Foundry Agent Service isn't supported starting November 6, 2026. Foundry tracing sends telemetry to Application Insights.

Best when: you already build agents in Foundry and need end-to-end traces for debugging and monitoring.

Where a data agent can be consumed (as documented when checked): the Fabric chat experience, Microsoft 365 Copilot (through the Agent Store), Copilot Studio (as a tool, or as a connected agent in preview), Microsoft Foundry (through the Fabric IQ tool, preview), and any MCP client through the published MCP endpoint. The approaches above simply pick a surface that also keeps the conversation.

Why this works

  • Copilot Studio offers two ways to use a published Fabric data agent. The newer one adds it as a tool (the Fabric IQ Data MCP tool) to an agent on the GitHub Copilot harness, which you can publish to Teams or Microsoft 365 Copilot. The earlier one adds it as a connected agent, which is in preview. Either way, the Fabric data agent still runs in Fabric with the permissions on its data sources.
  • Copilot Studio automatically saves transcripts to Dataverse by default (an environment setting controls this). Each record's Content column holds the conversation as JSON activities: user and agent messages, timestamps, channel, and a hashed user or conversation ID.
  • Link to Microsoft Fabric makes selected Dataverse tables available in OneLake through shortcuts, without building ETL. It creates a lakehouse, SQL analytics endpoint, and Power BI semantic model, and keeps them updated as Dataverse changes (the docs say updates can take up to 60 minutes).
  • Copilot Studio interactions are also in scope for Purview audit (Audit Standard), retention (a "Copilot Studio" location), and eDiscovery (item class IPM.SkypeTeams.Message.Copilot.Studio.*), so Approach B can sit alongside this one.
Preview, channel, and harness notes:
  • The connected agent option is in preview. Its docs say it is validated only for Microsoft Teams, other channels haven't been formally tested, and using it in Microsoft 365 Copilot isn't currently supported.
  • Transcripts aren't written for Microsoft Dataverse for Teams environments or for Microsoft Copilot agents.
  • The transcript articles note that the harness you build on affects features. They don't spell out transcript behavior per harness and channel, so confirm that your agent's conversations, including the data agent's answer text, actually appear in ConversationTranscript before you rely on it.
  • Some content can be redacted in transcripts. The transcript docs note that answers grounded in certain knowledge sources are marked REDACTED, with only the question and source content kept.
  • Responses returned by the Fabric data agent to Copilot Studio might leave Fabric's compliance boundary or geographic region and are handled under Copilot Studio's terms.

Why this works

  • When you publish a data agent you can choose Publish to Agent Store. People can then chat with it in Microsoft 365 Copilot, or mention it with @ from the main Copilot chat.
  • Purview stores data from generative AI messages in a hidden folder in the user's mailbox. Retention policies can target locations such as Microsoft 365 Copilot, Copilot in Fabric, and Copilot Studio.
  • Audit records for Copilot and AI interactions include properties such as AgentId, AgentName, the app host, and accessed resources. The Messages property holds message IDs and an isPrompt flag, not the prompt and response text. Audit records can also be pulled programmatically through the Office 365 Management Activity API.
  • DSPM for AI Activity explorer shows AI interaction events, and prompts and responses are included for users with the right permissions.
  • eDiscovery searches the mailbox item classes (for example IPM.SkypeTeams.Message.Copilot.Fabric.* for Copilot in Fabric) and can export results, which you can then land in OneLake for analysis.
Caveats to validate:
  • Purview capabilities for Fabric data agents specifically are described as preview, and the limitations say agent interactions "might be" logged and discoverable. Check that data agent turns actually appear before you rely on this path.
  • For Copilot in Fabric, DSPM for AI says prompts and responses are captured only if a collection policy like the one from the "Secure interactions for Microsoft Copilot experiences" recommendation is in place. Without it, audit events are captured but not the prompt and response content. The docs don't say explicitly whether in-Fabric data agent chats are classified as Copilot in Fabric.
  • This path is batch and case-oriented. It needs Purview and eDiscovery roles, and Purview licensing varies by capability, so check your entitlements.
  • Responses returned to Microsoft 365 Copilot might leave Fabric's compliance boundary or geographic region.

Why this works

  • A published data agent becomes an MCP server that exposes a single tool, at https://api.fabric.microsoft.com/v1/mcp/workspaces/{WorkspaceId}/dataagents/{DataAgentId}/agent. Any MCP client that supports streamable HTTP can call it with a Fabric bearer token (user or service principal) for the https://api.fabric.microsoft.com/.default scope.
  • Because your code sends each question and receives each answer, you can write both to your own store or OneLake at the moment of the exchange, with no dependence on a downstream transcript store.
  • You decide what to capture: question, answer text, timing, user, and your own session ID. The documented example reads the text content blocks that the tool returns.
  • For long questions, the endpoint supports the MCP tasks extension, so a client can poll for the result instead of holding a connection open.
Timing and design notes: The earlier programmatic path used the OpenAI Assistants API. The Fabric docs now state that OpenAI retired the Assistants API and that applications should use the MCP endpoint. Unlike the Assistants API, the MCP endpoint doesn't provide built-in conversation management, so your client maintains conversation state, which is also where you log it. Responses returned to an external MCP client might leave Fabric's compliance boundary or region and are handled under that client's terms.

What gets recorded where

  • Foundry tracing: after you connect an Application Insights resource to a Foundry project, server-side tracing is turned on automatically. Microsoft notes that tracing can capture sensitive information such as user inputs, model outputs, and tool arguments and results. The Foundry portal shows the last 90 days. Storage retention and cost follow your Application Insights and Log Analytics configuration.
  • Fabric data agent spans (preview): the data agent adds an agent span and one tool span per data source it queries. This telemetry is operational metadata only: agent display names, data source names, reasoning step IDs, conversation IDs, status, and duration. The docs state that user prompts and data agent responses aren't included. A Fabric tenant setting controls this and is on by default.
  • Purview: DSPM for AI can capture prompts and responses from applications built on Microsoft Foundry through its "Secure interactions from enterprise apps" collection policy. eDiscovery lists the item class IPM.SkypeTeams.Message.ConnectedAIApp.AzureAI.<AzureResourceName>.
Treat traces as debugging data, not a conversation archive. Content in traces depends on how your Foundry agent is built and instrumented, and the data agent's own spans carry no prompt or response text. The Application Insights resource might be outside your tenant's region or compliance boundary. Validate what actually lands in your traces after you switch to the Fabric IQ tool.

A common pattern: use Approach A when the goal is to save conversations and analyze them. Keep Approach B in place as the compliance and retention backstop, or use it when Microsoft 365 Copilot must be the surface. Use C for custom apps and D when the agent is built in Foundry.

Implementation walkthrough (Approach A)

1
Publish the Fabric data agent Confirm it answers correctly in Fabric, then publish it with a rich, detailed description. Copilot Studio's orchestrator uses that description to decide when to call it.
2
Add it to a Copilot Studio agent Use the same tenant and the same sign-in for Fabric and Copilot Studio. For the tool option, create an agent on the GitHub Copilot harness, open Tools, add Fabric IQ Data MCP, and select the data agent from the OneLake catalog. For the connected agent option (preview), go to Agents → Add → Microsoft Fabric and turn on generative orchestration.
3
Publish to a channel Publish and turn on the Teams channel, then test end to end that the Fabric data agent answers questions. If you share the agent with user authentication, each person needs read access to the data agent and its underlying data sources.
4
Confirm transcripts are saved and accessible In the Power Platform admin center, go to the environment → Settings → Product → Features and make sure Allow conversation transcripts and their associated metadata to be saved in Dataverse is on (it's on by default in new environments). An admin grants the Bot Transcript Viewer role to people who need to read transcripts. Optionally turn on enhanced transcripts (agent Settings → Advanced) for node-level detail. A recurring bulk delete job removes transcripts older than 30 days by default; replace it with a job on a longer schedule if you need more history.
5
Link Dataverse to Microsoft Fabric In Power Apps, go to Link data → New link → Fabric link (requires the System Administrator role in the environment). The wizard preselects tables with Track changes enabled, so confirm ConversationTranscript is selected. Linked tables consume Dataverse storage, and updates can take up to 60 minutes to appear in OneLake.
6
Parse the transcript JSON into curated tables The Content column is Bot Framework activity JSON. Use a Fabric notebook or dataflow to flatten it into tables such as conversation, turn (prompt and response), timestamp, hashed user, channel, outcome, and CSAT. Because the link reflects changes in Dataverse, plan for rows removed by the bulk delete job to disappear from the linked tables too, and persist curated history in your own lakehouse tables. As a low-code alternative, the Copilot Agent Kit's Conversation KPIs solution aggregates transcripts into Dataverse tables with sample Power BI reports.
7
Model and analyze in Power BI Build a semantic model for volume, active users, top questions, unanswered or abandoned sessions, themes, and response quality.

What's inside the transcript Content JSON

FieldMeaning
typeActivity type, for example message, event, or trace
textThe text of message activities (the actual question or answer)
from.role1 = user, 0 = agent
from.idHashed ID of the invoker. Unique per user if the channel passes a user ID, otherwise unique per conversation
timestampWhen the activity was generated (epoch format)
channelIdSource channel, for example msteams or directline
value / valueTypeActivity-specific data, such as SessionInfo (outcome, turn count), CSATSurveyResponse, IntentRecognition, and VariableAssignment

A transcript is saved after 30 minutes of inactivity. Records larger than 1 MB are split across rows that share Name and ConversationStartTime; merge them by sorting on BatchId in the Metadata column. Separately, Copilot Studio keeps session data in its own storage for up to 28 days, and its CSV session download truncates each agent response to 512 characters, so use the Dataverse table for full text.
