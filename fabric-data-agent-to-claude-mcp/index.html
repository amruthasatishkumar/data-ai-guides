Semantic model to Claude: a governed Fabric data agent path over MCP

Curate a semantic model, optionally add an ontology for shared business meaning, expose both through one Fabric data agent, then let Claude ask questions through the Model Context Protocol (MCP). This guide explains each layer, how identity works, and which parts are documented versus which you should test in your own tenant.

Independent explainer built from public Microsoft Learn and Anthropic documentation. Names such as Contoso and Sales semantic model are fictional examples. Labels used here: GA generally available, Preview preview or beta, Test an inference this guide makes that the docs do not state directly.

Foundation OneLake governed data: lakehouse, warehouse, mirrored database, KQL database. The semantic model and ontology add business meaning on top. Source data stays where it lives; the ontology binds to sources instead of copying them.

1 · Curate the semantic model

  • The data agent writes DAX against the model (NL2DAX), so clear table, column and measure names and descriptions directly shape answer quality.
  • To query a semantic model through a data agent, a user needs Read on the model. Build and workspace access aren't required for agent queries. Build or Write is still needed to change the model or to use features such as Prep for AI.
  • Row-level security (RLS) and column-level security (CLS) continue to apply to agent queries.

Sources: How the data agent works, Data agent sharing and permissions.

2 · Generate the ontology Preview

  • An ontology defines business concepts (customers, products, orders), their properties, relationships, rules and metrics, then binds them to data. It is a context layer, not a separate data store.
  • Generate Ontology on a semantic model creates entity types from tables, properties and bindings from columns, relationship types from model relationships, and metrics from DAX measures. The semantic model stays the owner of each DAX expression.
  • After generation, do the manual steps: bind time series data, review entity type keys, bind relationship types, rename to friendly names, and review the whole ontology.
  • Tenant settings Users can create ontology (preview) items and Users can create Fabric items must be enabled.
  • Permissions differ between docs. The ontology generation page says Read and Build on the semantic model are needed to generate an ontology and to query the semantic model through the ontology. The data agent sharing page lists Read on the ontology item plus Read on the bound sources. Test with a Read-only pilot user before rollout.
  • When the semantic model changes, review the ontology and rerun your test questions. (Recommended practice, not a documented sync rule.)

Sources: What is ontology (preview), Generate ontology from semantic models, Data agent sharing.

3 · Create the data agent

  • Prerequisites: a paid F2 or higher Fabric capacity (or Power BI Premium P1 or higher with Fabric enabled), and the tenant settings for cross-geo processing and storing for AI, as required.
  • Up to five data sources in any combination: lakehouses, warehouses, KQL databases, Power BI semantic models, ontologies, mirrored databases and Microsoft Graph.
  • The agent picks a source, writes SQL, DAX or KQL, validates it, and runs it read-only with the requesting user's credentials. Purview DLP and access restriction policies on the sources are respected.
  • Add instructions for routing and terminology. Example question and query pairs help for SQL and KQL sources, but they aren't supported for semantic model sources.
  • Sharing the agent is not enough: users also need permission on each underlying source. With the default share permission, users can query only the published version.

Sources: Fabric data agent concepts, Data agent sharing.

4 · Publish as an MCP server, then connect Claude

  • After you publish, open the agent's Settings > Model Context Protocol tab for the server name, server URL, tool name and tool description, or download mcp.json.
  • URL format: https://api.fabric.microsoft.com/v1/mcp/workspaces/{workspaceId}/dataagents/{dataAgentId}/agent. It works only for a published agent.
  • The published description becomes the MCP tool description that Claude reads to decide when to call the agent. Make it specific.
  • Every request needs a bearer token for a user or a service principal, requested for the scope https://api.fabric.microsoft.com/.default.
  • The server does not support dynamic client registration or client ID metadata documents. The client must get a Fabric token through its own flow. See the identity options below.
  • For long questions the server supports the MCP tasks extension; clients without it get the answer on the same connection.
  • Answers returned to an MCP client may leave Fabric's compliance boundary or region and are then handled under that client's terms.

Source: Data agent as Model Context Protocol server. The data agent itself is generally available; this Learn page carried no preview label when checked on November 6, 2026.

Connecting Claude: identity options

The data agent endpoint needs a Fabric token on every request and can't register Claude automatically. Pick the Claude surface you plan to use to see what is documented and what you need to test.

Microsoft (documented)No dynamic client registration (DCR) or client ID metadata document (CIMD) support. The client uses its own auth flow and sends a token for https://api.fabric.microsoft.com/.default.
Anthropic (documented)Custom connectors identify Claude by CIMD ("Use Claude's published identity"), by DCR ("Register automatically"), or with "Use your own OAuth client". Only the last fits this endpoint.
Observed on Nov 6, 2026An unauthenticated call to the endpoint returned 401 with a resource_metadata pointer naming Microsoft Entra as the authorization server and the Fabric .default scope. The Power BI MCP endpoint returned the same metadata.

Custom connector with your own Entra app Test before rollout

Documented
  • Team and Enterprise: an Owner adds the connector in Organization settings > Connectors > Add > Custom. Members then connect with their own account. On individual plans you add it yourself.
  • Under OAuth client, choose Use your own OAuth client and enter a client ID. Leave the secret blank unless the authorization server requires one.
  • Hosted Claude apps (web, Desktop, mobile) use the redirect URI https://claude.ai/api/mcp/auth_callback.
  • Microsoft documents this exact pattern for the Power BI MCP servers: a single-tenant Entra app, a Mobile and desktop applications redirect with the Claude callback URL, delegated Power BI Service permissions, and the app's client ID in Claude.
  • Connector traffic comes from Anthropic's infrastructure (Anthropic publishes its egress IP ranges), not from the user's device.
Inference to test
  • Because the data agent endpoint is on the same host and advertises the same Entra metadata as the Power BI MCP endpoint, the same own-app pattern is likely to work. Microsoft doesn't document Claude for the data agent endpoint.
  • Microsoft doesn't list which delegated permissions a custom app needs for the data agent endpoint. Start a pilot app registration and confirm sign-in, consent and a real answer.
  • If your tenant restricts inbound access to Fabric (for example private links) or uses location-based Conditional Access, calls from Anthropic's cloud may be blocked. Check with your identity and network teams.
Pilot steps
  1. Register a single-tenant app in Microsoft Entra ID, for example Contoso Sales agent - Claude.
  2. Add the redirect URI https://claude.ai/api/mcp/auth_callback under Mobile and desktop applications, as Microsoft's Power BI guidance shows.
  3. Add the delegated Power BI Service permissions your tests show are required; grant admin consent if your tenant requires it.
  4. In Claude, add a custom connector with the agent's MCP server URL, choose Use your own OAuth client, and paste the client ID.
  5. Connect, sign in, ask a known question, and compare the answer with the same question in Fabric.
Authentication settings can't be edited after a connector is added. To change them, remove and re-add the connector; members then reconnect.

Claude Code on a developer machine Documented parts, untested combination

Claude Code documents two building blocks that match Microsoft's "bring your own token" requirement. The combination with the data agent endpoint isn't documented end to end, so test it.

Option A: dynamic header (headersHelper)

Claude Code runs a command at connect time and merges its JSON output into request headers. The command can fetch a Fabric token for the signed-in developer, so the agent applies that person's permissions and RLS.

{
  "mcpServers": {
    "contoso-sales-agent": {
      "type": "http",
      "url": "https://api.fabric.microsoft.com/v1/mcp/workspaces/<workspaceId>/dataagents/<dataAgentId>/agent",
      "headersHelper": "/usr/local/bin/fabric-mcp-header.sh"
    }
  }
}
#!/usr/bin/env bash
# fabric-mcp-header.sh: prints the Authorization header as JSON
TOKEN=$(az account get-access-token \
  --scope https://api.fabric.microsoft.com/.default \
  --query accessToken -o tsv)
printf '{"Authorization": "Bearer %s"}' "$TOKEN"

The helper runs at session start and on reconnect, isn't cached, and must finish within 10 seconds. Access tokens expire, so a long session may need a reconnect.

Option B: pre-configured OAuth client

For servers without DCR, Claude Code accepts your own client ID and a fixed callback port.

claude mcp add --transport http \
  --client-id <entra-app-client-id> --callback-port 8080 \
  contoso-sales-agent \
  https://api.fabric.microsoft.com/v1/mcp/workspaces/<workspaceId>/dataagents/<dataAgentId>/agent

Register http://localhost:8080/callback on the Entra app. Use only --client-id for a public client with no secret.

Long-running questions

Static request header Beta Not recommended here

Documented
  • Request headers on custom connectors are in beta for a limited set of organizations.
  • An Owner enters a fixed credential once; Claude sends it on every request from every member.
  • Anthropic says to treat it as the organization's credential, not a person's, and to use OAuth when tools must act as the individual user.
Why it is a poor fit
  • Fabric expects a Microsoft Entra access token. These tokens are short-lived, so a pasted token stops working.
  • One shared identity means answers no longer reflect the asker's own permissions or RLS.

Your own MCP gateway Custom build

A design pattern, not a documented Microsoft or Anthropic recipe. You host a small MCP server that Claude can connect to and that calls the data agent endpoint with a Fabric token.

Identity choices
  • Per user: exchange the signed-in user's token for a Fabric token (for example with an Entra on-behalf-of flow) so the agent still applies each user's permissions. Validate that the endpoint accepts these tokens.
  • Service principal Preview: one identity for everyone. Needs the tenant setting Service principals can use Fabric APIs, workspace access, and read access on every source. Not yet supported for KQL sources; managed identities aren't supported.
Things you own
  • Token handling, logging, patching, and keeping up with MCP changes.
  • If the gateway is private, Claude can reach it through MCP tunnels Research preview, available on the Enterprise plan by request.
  • Claude doesn't support a machine-to-machine client_credentials grant between Claude and your server; users still sign in.

Validate the endpoint with a documented client first Documented

Before you troubleshoot Claude, prove the agent, permissions and token work with a client Microsoft documents: Visual Studio Code (add an HTTP MCP server and sign in) or a short Python script using the MCP Python SDK and azure-identity.

pip install mcp azure-identity
# Sign in with an account that can use the agent and its sources
az login
# Then follow the Python sample on the Microsoft Learn page:
# AzureCliCredential().get_token("https://api.fabric.microsoft.com/.default")
# initialize -> tools/list -> tools/call with your question

If this works but Claude doesn't, the problem is the Claude-side OAuth setup, not the agent.

Governance and boundaries

Identity

  • Claude can't self-register with this endpoint: no DCR and no CIMD.
  • Use per-user tokens when answers must respect each person's permissions.
  • Service principal auth for data agents is preview, not for KQL sources, and gives everyone the same view.

Security is inherited

  • Queries run read-only with the caller's Fabric permissions.
  • RLS and CLS apply to agent queries; source permissions are required in addition to sharing the agent.
  • Purview DLP and access restriction policies on sources are respected.

Data leaves the boundary

  • Answers sent to Claude may leave Fabric's compliance boundary and region.
  • Claude's terms and data handling then govern them.
  • RLS limits what Fabric returns, not what the client stores. Review tool approvals and block tools you don't need.

Preview & quality

  • Preview or beta: ontology, data agent service principal auth, Purview features for data agents, Power BI MCP servers, Claude request headers, MCP tunnels, Claude Code MCP tasks.
  • Recheck limits before production; they change often.
  • Validate answers with a ground-truth question set before rollout.
